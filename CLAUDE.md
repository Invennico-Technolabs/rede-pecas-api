# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Rede Peças — central API backend for a WhatsApp AI sales agent (auto parts marketplace in Angola) and its admin approval panel. The AI agent converses with customers over the Meta WhatsApp Cloud API, identifies their vehicle (VIN or guided steps), searches inventory, generates proforma PDFs, and walks them through payment; staff approve orders via the admin API (consumed by the separate `rede-pecas-admin` React repo at `D:\Invennico\rede-pecas-admin`).

## Commands

```bash
npm run dev        # tsx watch, watches src/
npm run build      # tsc → dist/
npm start          # node dist/index.js (requires build)
npm run lint       # eslint src
npm run db:migrate # apply db/schema.sql to DATABASE_URL
npm run db:seed    # migrate + insert db/seed.sql sample data (safe to re-run — resets seed products to canonical qty/price)
npm run db:clear   # wipe DB data + flush Redis (db/clear.js) — always both together, see the file's header comment for why
npm run docs:flow  # regenerate the message-pipeline flow doc from scripts/flow-content.js
npm run admin:cli  # interactive terminal CLI to drive stock-confirmation/payment approval while testing WhatsApp locally (no admin panel UI needed) — see scripts/admin-cli.js
```

There are no automated tests yet (no test runner is configured). `TESTING.md` is the manual test matrix — run `npm run db:seed` first, then work through it against a running `npm run dev` instance. Note: the WhatsApp Business number is in Meta's sandbox mode, so it can only send to phone numbers explicitly added to the app's allowed-recipient list.

Boot requires a `.env` at the project root (copy `.env.example`) — `src/config/config.ts` throws at import time if any of these are missing: `DATABASE_URL`, `ANTHROPIC_API_KEY`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_VERIFY_TOKEN`, `JWT_SECRET`. Redis (`REDIS_URL`) is optional — sessions fall back to an in-memory Map. Admin login needs at least one row in `admin_users` — `db/seed.sql` inserts a dev account (`admin@redepecas.ao` / `admin123`).

## Critical conventions

- **Language split**: code identifiers, DB tables/columns, stored status values, API routes, and JSON payload keys are **English**. **As of 2026-10-26, the customer-facing conversation language is Angolan Portuguese by default and changes only by the customer's explicit choice — it is never detected from message text.** The per-message `detectMessageLocale`/`detectGreetingLocale` (2026-07-17 to 2026-10-26) were removed after QA showed an isolated "Hi" flipping an Angolan customer's whole conversation to English. The choice is the 🌐 option — a `🌐 English`/`🌐 Português` button on the first welcome message (`customerService.sendWelcome`) and the last row of the main-menu list (`sendMainMenu`), both with id `SWITCH_LANGUAGE_ID` (`lang_switch`), routed in `processMessageFlow` right after the stale-tap check (before registration, so a tap is never taken as the customer's name) to `customerService.switchLanguage`, which toggles pt⇄en, saves it to **`customers.locale`** (durable across sessions, default `'pt'`), confirms in the new language, and re-sends the welcome or the menu. `resolveLocale(phone)` reads the session cache (`sessionService.saveLocale`/`getLocale`, 4h `SESSION_TTL`), else `customers.locale`, else `DEFAULT_LOCALE`. Every customer-facing WhatsApp send across the message pipeline (registration, vehicle ID, product search, payment/order flow) and the proforma/invoice PDFs (`pdf.service.ts`'s `generateProformaPDF`/`sendProformaWhatsApp`/`generateInvoicePDF`/`sendFinalInvoiceWhatsApp` all take an explicit `locale` param now, instead of the fixed `t`) resolves through `resolveLocale(phone)`/`resolveMessages(phone)` (`customer.service.ts`) — session cache, then the customer's saved `customers.locale`, falling back to `DEFAULT_LOCALE` (`src/i18n/messages.ts`, a hardcoded `'pt'`, no longer sourced from any env var). The old `MESSAGE_LOCALE` env var is gone entirely; the fixed `t` export in `messages.ts` is now hardcoded to the English variant and still backs the paths that are deliberately **not** customer-locale-aware: admin-panel/admin-push messages (`adminAuth.service.ts`, and every `t.admin.*` call in `payment.service.ts`/`product.service.ts`) and the supplier delivery notice (`payment.service.ts`) — none of those are "the customer greeting the bot". Also note: the full-text search config is **not** `'portuguese'` (an earlier version of this note claimed it was) — `db/schema.sql`'s `search_vector` and `product.model.ts`'s `AND_TSQUERY`/`OR_TSQUERY` all build on the `'english'` config (`to_tsvector`/`plainto_tsquery`/`to_tsquery`) as of the 2026-07-14 English catalog-data switch, so Portuguese-specific stemming doesn't apply to either language's search terms today (lexeme/substring matching still works regardless). The two AI vision-extraction prompt bodies (`src/services/ai.service.ts`) are unrelated to any of this — they were already switched to English earlier (2026-07-10) for a different reason (Claude reasons more reliably in English on them), since the model never sees customer text at all.
- **ESM with NodeNext resolution**: `"type": "module"` + `moduleResolution: NodeNext`. All relative imports **must use the `.js` extension**, even inside `.ts` files (`import { config } from '../config/config.js'`). Omitting it breaks the build.
- Layering is `routes → controllers → services → models`, with raw `pg` queries in `src/models/` (no ORM) against a shared `Pool` from `src/config/db.ts`. Config is only read via the `config` object, never `process.env` directly.
- **Schema lives in `db/schema.sql`** (with `db/seed.sql` and `db/schema.dbml` for dbdiagram.io). SQL in models must match it — when you change one, change all three.
- **Every admin API response shares one envelope** — success: `{ success: true, message, code, data, [accessToken], [refreshToken], meta: { timestamp } }`; error: `{ success: false, message, code, data: null, meta: { timestamp } }`. No stack trace is ever sent to the client (logged server-side only via `logger.error`, in `errorHandler`). There's no shared response-builder function — each controller writes its own `res.status(code).json({...})` literally; only the shape is a convention, not a helper. The WhatsApp webhook endpoints are one exception (see below) — Meta's contract requires a bare 200 / raw challenge string, not this envelope. `/orders/:number/payment/proof` (see below) is a second, deliberate exception — it streams the raw image/PDF bytes with an `image/jpeg`/`application/pdf` Content-Type, since binary bytes can't usefully be wrapped in JSON.
- Errors: throw `ApiError` (from `src/utils/ApiError.ts`), wrap async route handlers in `catchAsync`; `errorConverter`/`errorHandler` in `src/middlewares/error.ts` produce the error envelope above. `validate(schema)` (`src/middlewares/validate.ts`) humanizes Joi's raw quoted-field messages (`"newPassword" is required` → `New Password is required`) before wrapping them in an `ApiError`. Admin routes validate input with Joi schemas in `src/validations/`.
- Logging goes through the Winston `logger` in `src/config/logger.ts`, not `console`.

## Architecture

Two route groups mounted under `/v1` (`src/routes/v1/index.ts`):

- `/v1/webhook/whatsapp` — Meta webhook. GET is the verification handshake; POST is the message intake: it first verifies Meta's `X-Hub-Signature-256` HMAC over the raw body (`src/middlewares/whatsappSignature.ts`, keyed by `WHATSAPP_APP_SECRET` — required in production, skipped with a boot warning when unset locally; a bad/missing signature gets a bare 401), then **responds 200 immediately** (Meta's 5-second rule), drops duplicate deliveries of the same `msg.id` (`sessionService.claimInboundMessage`, Redis `SET NX`, 24h), and processes asynchronously. Errors after that point are logged, never returned to Meta.
- `/v1/admin` — JWT-protected via `authMiddleware` (access-token payload: `{ id, email, role }`), individual accounts in `admin_users` (bcrypt password hashes, `adminAuth.service.ts`): `/login` (returns an access token — `JWT_ACCESS_EXPIRATION_MINUTES`, 60 min code default, `.env.example` sets 480 — + a refresh token, 30d default, JWT with `type: 'refresh'` — `authMiddleware` rejects a refresh token used as a bearer token on any other route), `/refresh` (exchanges refreshToken for a new accessToken, no rotation), `/logout` (revokes both the current access token and the supplied refresh token — `sessionService.revokeToken`, a hashed-token blacklist kept for each token's remaining lifetime and checked by `authMiddleware`), `/forgot/password` + `/reset/password` — identified by **phone**, not email (body: `{ phone }` / `{ phone, code, newPassword }`), since the 6-digit code is delivered over WhatsApp to that same number and there's no email/SMTP service in this project; `getAdminByPhone` compares digits-only so formatting in the stored `phone` column doesn't matter, `/profile` (GET/PATCH), `/change/password`; plus `/orders` list (`data.pending`/`data.approved`/`data.rejected`/`data.stockConfirmation`, pending first — pending/approved/rejected rows all carry `has_proof`/`payment_proof_media_type`), `/orders/:number/review` (body `{ approved: boolean }` — merges the old separate approve/reject endpoints), `/orders/:number/confirm/stock` (body `{ available: boolean }` — merges the old separate confirm/stock-unavailable endpoints), `/orders/:number/payment/proof` (GET, binary — streams the customer's uploaded payment-proof photo/PDF straight from Meta's Graph API via the existing `downloadWhatsAppMedia`, since the file itself is never stored on our infrastructure, only Meta's `payment_proof_media_id`), `/alerts` + `/alerts/:id/read` (the admin notification feed — see below), `/inventory/upload` + `/inventory/import` batch import. Route segments use `/` nesting, never hyphens. The admin panel (`rede-pecas-admin`) depends on these exact paths and payload keys (order fields `number, customer, part, reference, supplier, price, time, has_proof` — see the envelope convention above).

### Admin notifications: both an in-panel alert feed and WhatsApp pushes

`admin_alerts` (`src/models/alert.model.ts`) is a durable in-panel feed (note: as of 2026-10-26 the `rede-pecas-admin` panel does not actually consume `/alerts` yet — the WhatsApp pushes are what admins see) — `createAlert(type, orderNumber | null, message)` is called from `payment.service.ts` on payment-proof-received and in-person-payment-requested, and the admin panel polls `GET /v1/admin/alerts` (newest first, capped at 100) / `POST /v1/admin/alerts/:id/read` to dismiss. Alongside that, `payment.service.ts` also pushes a WhatsApp message to every row in `admin_users` (`getAllAdmins()`, not a single shared number — the old `config.admin.staffPhone`/`STAFF_PHONE_NUMBER` pattern was removed entirely) for the same events, plus the pre-existing stock-confirmation-needed push:
- **Stock confirmation needed** and **in-person payment requested** are plain text messages (`t.admin.stockConfirmationNeeded` / `t.admin.inPersonPaymentRequested`).
- **Payment proof received** is sent as an interactive message with the proof photo/PDF as the header (reusing the `media_id` Meta already issued for the inbound proof — no re-upload) and **Approve/Reject buttons attached directly** (`admin_approve_payment_<order>` / `admin_reject_payment_<order>`), handled by `processAdminPaymentReply` in `payment.service.ts` — the WhatsApp-native equivalent of the panel's `POST /orders/:number/review`, so either surface reaches the same outcome. Routed in `whatsapp.controller.ts`'s admin short-circuit by button-id prefix, alongside the stock-confirmation buttons (`processAdminStockReply`).
- None of these admin messages link to the panel anymore (`config.appUrl` was previously appended as `🔗 {url}/admin/orders`) — replaced with a plain "check the Rede Peças admin platform" line, since the buttons (where present) act directly from WhatsApp.

There is still no email notification — none exists in this codebase and none was added to scope.

### The message pipeline (the heart of the system)

`processMessageFlow` in `src/controllers/whatsapp.controller.ts` routes every incoming message through a strict priority chain — earlier stages short-circuit later ones. Messages from the same phone are processed one at a time in arrival order (`runSerialized` in `src/utils/keyedQueue.ts`, in-process — moving to multiple API instances would need a shared Redis/BullMQ lock instead).

Customer profile registration and vehicle identification are **independent state machines**, each with its own status, so whichever is missing is what the bot asks for next — a returning customer whose vehicle session simply expired is sent back into the vehicle-ID flow without re-doing their profile:
- **Profile**: `customers.registration_status` — `awaiting_name → awaiting_nif → awaiting_nif_number → awaiting_address → complete`. Covers name/NIF/address only.
- **Vehicle ID**: derived on every message from the `vehicles` table itself (no ORM/status field on `customers`) — `needsVehicleId` is true when the profile is `complete`, there's no in-progress manual-entry wizard, and `vehicleService.hasVehicleOnFile` finds no confirmed row. There is no separate "awaiting" status to keep in sync; the table's own shape (absent row / in-progress wizard step / confirmed row — see `vehicle.model.ts`) is the state.

**A customer can have multiple confirmed vehicles.** `vehicles.id` is the primary key (not `phone` — a customer can have several rows). `vehicleService.startAddVehicleFlow` re-runs the same VIN/photo/manual choice on demand (triggered by the "➕ Outro carro"/"➕ Add vehicle" button always offered alongside the ask-part prompt, or the same phrase typed free-text — `vehicleService.isAddVehicleRequest`), and `saveVehicleSession` always inserts a new row unless given a specific in-progress row's `id`, so existing vehicles are never touched by adding another. When a search is about to happen and the customer has 2+ vehicles, `sendAskPartPrompt` asks "which vehicle is this for?" first (`sessionService.savePendingVehicleChoice`/`getPendingVehicleChoice`) and `ai.service.ts` uses the resolved choice (`sessionService.getChosenVehicle`) instead of guessing.

Pipeline order (as of 2026-10-15 — re-check against `processMessageFlow` if this has drifted):

0. **Admin short-circuit** — sender phone matches an `admin_users` row: only button replies are handled (payment approve/reject → `processAdminPaymentReply`, `admin_item_*` → `processAdminItemStockReply`, everything else → `processAdminStockReply`); plain admin text is ignored. Nothing below runs for admins.
1. Last-message cache for the humanize layer and the chat transcript (`appendChatMessage`). No locale detection — see "Language split".
2. Customer lookup/create. A deactivated customer (`customers.active = false`) gets `common.accountInactive()` and every admin is pushed `admin.inactiveCustomerAttempt` — at most once per customer per 6h (`sessionService.claimInactiveCustomerAlert`).
3. **Fresh session** (no `active:<phone>` key in the last 4h): profile+vehicle complete → a greeting or interactive tap gets the main menu (`customerService.sendMainMenu`: welcome + a list of 🔎 Search parts / 📦 Order status / ➕ Add vehicle / 🌐 English|Português — no vehicle question on a greeting), any other text gets `welcomeBack` and is then processed as a request below, media gets `welcomeBack` and falls through; vehicle missing → resume vehicle-ID buttons; profile incomplete → `sendResumeRegistrationPrompt`.
4. Stale interactive reply — a button/list tap whose `context.id` isn't the latest prompt we sent (`getActivePromptId`) → `common.alreadyAnswered()`. Then the 🌐 language option (`lang_switch` → `switchLanguage`), then main-menu list taps (`menu_search_parts` → `sendAskPartPrompt`, `menu_order_status` → `handleOrderStatusRequest`, `menu_add_vehicle` → `startAddVehicleFlow`).
5. `order_status_<number>` button (on the final invoice) → `orderStatusService.processOrderStatusButton`. **In code this runs right after step 2, before the fresh-session check (step 3) and before `markSessionActive`** (as of 2026-10-27): approval calls `resetSearchSession` (and a late tap finds the session expired), so step 3 would otherwise turn the tap into the main menu; not marking the session active keeps the next message a fresh session (greeting/tap → main menu).
6. Profile registration (name → NIF → address) while `registration_status !== 'complete'`.
7. Explicit "add another vehicle" request (button or typed) — only once the customer already has at least one vehicle.
7a. Shared WhatsApp location (`msg.type === 'location'`, parsed in the webhook; in code this runs right after the step-4 taps, before step 5, since a location has no text and would otherwise be dropped by the `!customerText` guard) → `orderProfileService.processOrderProfileLocation` when the order-profile wizard is at its address step (stores lat/lng in `customers.address_lat/address_lng`; if WhatsApp attached a place name/address — the customer picked a named place — that becomes the readable `customers.address` and the wizard moves straight on; only a bare "current location" pin with no text asks one "ponto de referência" landmark — stage `awaiting_address_landmark` — making the address "Ref. landmark"); anywhere else `common.locationNotNeeded()`. The address prompts themselves are sent as WhatsApp's native location request (`sendReplyLocationRequest`), and a typed address still works as before (validated by `validateFreeText`, coordinates NULL). Admin pushes that show the address append a 🗺️ Google Maps link when coordinates exist (`formatAddressWithMap`); an admin-panel address edit clears them.
7b. Supplier-inquiry details — after a customer accepted "should our team check with suppliers?" (see 17): the next part photo or typed reference/description (not a greeting, courtesy or button tap) → `productService.submitSupplierInquiry`, which pushes it to every admin over WhatsApp (photo re-sent by media id via `sendWhatsAppImage`, with customer/phone/vehicle/original query), logs an `admin_alerts` row (`type = 'supplier_inquiry'`, `order_number` NULL), and tells the customer the team will contact them directly. Must stay before image routing (10/11), or the photo would be taken as a vehicle document or payment proof.
8. Document-retry choice, then VIN-decode-failed choice (each gated on its own session flag).
9. Vehicle-ID option button tap (VIN / photo / manual), whenever `needsVehicleId` or the choice buttons were just shown.
10. State-aware image routing: while vehicle ID is needed (missing, active manual collection, or choice buttons just shown), an image is a vehicle document (`processVehicleDocument`, Claude Vision).
11. Any other image/document → payment proof (`processPaymentProof`). Media with no text stops here.
12. Active manual vehicle collection (make → model → year → engine number). As of 2026-10-27 each make/model/year reply first goes through `ai.service.ts`'s `extractVehicleDetails`, so a reply carrying several fields ("Toyota Corolla ano 2009 motor 2ZR") fills them all and the answered steps are skipped; the current step's field is strictly validated (re-ask), volunteered extra fields are silently dropped if invalid. Engine codes are ignored — the engine-number step is still asked.
13. 17-char VIN → NHTSA decode → confirm buttons.
14. Pending "which vehicle is this for?" reply (2+ vehicles) — must resolve before the yes/no/numeric offers below.
15. VIN-already-registered choice.
16. Pending part-type choice (OEM/Aftermarket/New/Second Hand list) → runs the actual search(es) — see 26.
17. Pending offers, in this order: waitlist opt-in, basket waitlist opt-in, supplier-inquiry offer (sent instead of a dead-end "not found" when a single search or every basket item matched nothing at all — not even an out-of-stock listing; yes → ask for photo/reference, see 7b), add-on service selection, stock-unavailable choice, order-profile "use saved details" shortcut, order-profile wizard step, restock re-order.
18. Vehicle confirmation reply (Sim/Não) — "Não" deletes only the just-rejected row. First-ever confirmed vehicle stamps `registered_at` and sends the combined welcome.
19. `needsVehicleId` still true and nothing matched: a greeting re-sends the vehicle-ID buttons; a VIN-shaped wrong-length string gets `vin.invalidLength`; anything else gets `common.notUnderstood()` + the buttons.
20. Order awaiting payment input (`awaiting_payment_method` / `awaiting_bank_subtype`).
20a. (in code, right after the step-21 greeting check) Order whose payment is chosen but not approved (`awaiting_payment_proof` / `payment_proof_received` / `awaiting_agent_confirmation` — `paymentService.getPostPaymentOrder`): a text message (not a tap, handoff, courtesy or status keyword) that `extractProductNames` judges is **not** a part request gets `paymentService.sendPostPaymentStatus` — a proof reminder, or "we're verifying your payment" + the main menu — instead of the part-search prompts; a real part request continues to a normal search, reusing the extraction. On approval, `approveOrder` calls `sessionService.resetSearchSession` so the next message starts fresh.
21. A greeting (`GREETING_PATTERN`, always wins) from a customer with a vehicle on file → the main menu (as in step 3). Part-search gate: free text is only a search once the part prompt or main menu was sent this session (`wasPartPromptSent`); otherwise `sendAskPartPrompt` is sent.
22. Reply to a just-shown results list (`getPendingOptions`) → `processAlternativeSelection` (substitute for an unavailable order line) or `processBasketProductSelection`; non-selection-shaped text falls through to a fresh search.
22b. Any button/list tap still unclaimed here answers a question that was already answered (e.g. a second payment-method tap after one was chosen — the reply was plain text, so step 4 still sees that prompt as the latest) or whose state was lost — it is **never** searched as a part name and **never resets** the conversation (no main menu). `orderProfileService.resumeOrderProfileCapture` restarts the profile wizard for the customer's latest `awaiting_customer_details` order under 4h old (stock confirmed, proforma never sent); otherwise just `common.alreadyAnswered()` and the flow continues from where it is. (Step 21's part-prompt gate also ignores taps.) Related: `finalizeOrderProfile` saves the profile **before** clearing the wizard stage, so a failed DB write can't strand the order.
23. Human handoff — keyword match (`HUMAN_HANDOFF_PATTERN`).
24. Courtesy message ("Ok", "thank you for the support", "ok obrigado pela ajuda" — `isCourtesyMessage` in `src/utils/greeting.ts`: text only, every word must be courtesy vocabulary, at least one a core thanks/ok word) → never searched as a part name; gets one `common.courtesyReply()` ("You're welcome! …"), at most once per 10 minutes (`sessionService.claimCourtesyReply`) so a thanks → reply → "ok" chain doesn't loop. If the courtesy closes a "nothing found" reply (supplier-inquiry offer still pending), `sessionService.resetSearchSession` wipes the search state and the `active:` key, so the next message starts a fresh conversation (new session → main menu on a greeting). Order-in-progress keys are never touched.
25. Order-status keywords (`ORDER_STATUS_PATTERN`) → `orderStatusService.handleOrderStatusRequest`.
26. Fallback — **only for an actual part request.** First `isBareReply` (`src/utils/greeting.ts`: bare yes/no, a 1–2 digit number, or an individual-NIF-shaped string) is rejected deterministically; otherwise `extractProductNames` runs, and an **empty** result (Claude judged it's not a part request — a question about delivery/payment, a name, an address, small talk…) is rejected too. Either way the customer gets `agent.notAPartRequest()` and **no search starts**; only a `null` (extraction failed) fails open to searching the raw text. Then, if no vehicle has been picked this session, `askVehicleChoiceForRequest` holds the request (`saveDeferredPartRequest`) and asks "which vehicle is this for?" (numbered list even for one vehicle, plus ➕ Add vehicle); the pick (step 14) resumes it. Then `productService.beginPartTypeChoice`: `extractProductNames` (Claude, see below) splits the message into one or more part phrases → `savePendingPartTypeChoice` → `sendPartTypePrompt`. The deterministic full-text search (`searchAndRespond`, or the basket queue for 2+ parts) only runs once the part type is picked at step 16.

New message-handling behavior must slot into this chain deliberately — position determines what can intercept what.

As of 2026-07-20, every strictly button-driven choice (vehicle-ID picker, document-processing retry, VIN-already-registered, vehicle Sim/Não confirm, bank transfer/deposit subtype) re-asks the same question (`messages.common.notUnderstood()` + the original buttons) when the reply doesn't match an expected option, instead of falling through the rest of the pipeline — the previous behavior silently started manual vehicle-entry with whatever the customer typed, or (for the payment subtype) silently guessed one of the two options. This required a new `vehicleConfirmShown` session flag (`session.service.ts`) since the vehicle-confirm step previously had no gate at all — it just regex-matched sim/não against every message that reached that stage, which would have made a blind re-ask unsafe. The 4 "pending offer" yes/no prompts (waitlist notify, add-service, stock-unavailable alternatives, restock-reorder) deliberately keep the old fall-through behavior — an unmatched reply there is more likely to be a genuinely new request (e.g. a fresh part search) than a misunderstood answer.

### Conversational state

State is per-phone-number and lives in two places:

- **PostgreSQL** — durable step-machine state: `customers.registration_status`, `vehicles.status` (the merged per-customer vehicle-identification table — see below), and `orders.status` (state machine in `src/services/payment.service.ts`: `awaiting_payment → awaiting_payment_method → awaiting_bank_subtype → awaiting_payment_proof | awaiting_agent_confirmation → payment_proof_received → approved | rejected`). As of 2026-07-20, `awaiting_bank_subtype` (transfer vs deposit) is the only payment sub-choice left — the old `awaiting_in_person_subtype` step is gone: tapping "Mobile POS (TPA)" now confirms that method directly instead of opening a redundant "TPA (cartão) or Dinheiro" sub-menu, and cash-on-delivery (`payment_method = 'cash'`) was dropped entirely as a customer-selectable option (WhatsApp reply buttons cap at 3, and Bank/Multicaixa/Mobile POS already fill them). Before that chain, orders pass through `awaiting_stock_confirmation` (admin confirms availability) → `stock_unavailable` (terminal) | `awaiting_customer_details` → `awaiting_payment_method`. **As of 2026-10-27 the order is: product selected → order created → supplier stock confirmation → (confirmed) individual/company + address + NIF capture (`startOrderProfileCapture`, or the "use saved details" shortcut for returning customers) → order review summary (items, total, customer type/NIF, address — informational, no confirm step) → proforma PDF → payment method** (`sendProformaAndAskPayment` in `product.service.ts`, called when the profile capture completes). Previously the address/NIF were collected before stock confirmation; that was reversed so customers aren't asked for delivery details for a part that may turn out unavailable. As of 2026-07-31, a multi-item basket order with at least one (but not every) item unavailable moves to a distinct `awaiting_alternative_resolution` status instead of staying at `awaiting_stock_confirmation` — every currently-known item has an admin decision, and it's the customer's turn to pick a substitute per rejected item, so the 10-minute customer courtesy message and 5-minute admin-reminder (20/15 before 2026-10-27) sweeps (both gated on `status = 'awaiting_stock_confirmation'`, and both measured from `orders.stock_confirmation_requested_at` — stamped by `updateOrderStatus` each time an order enters that status — never from `created_at`, which predates the per-order NIF/address step and used to make "sorry for the delay" fire right after "let me check with the supplier") correctly stop nagging while nothing is awaiting an admin decision. The order stays visible in the admin panel's stock-confirmation view either way (`getOrdersPendingStockConfirmation` fetches both statuses) — the admin panel just renders it as "waiting on customer" instead of actionable, rather than showing the legacy single-product Approve/Reject buttons once every item had a decision (those call the whole-order `{available}` body, which is meaningless for a basket — `product_id`/`unit_price` are NULL there). Returns to `awaiting_stock_confirmation` once a swapped-in alternative needs its own admin confirmation (`finalizeMultiItemOrder`/`processAlternativeSelection` in `product.service.ts`).
- **Redis** — every per-phone session flag/offer/cache (pending search options `options:<phone>`, baskets, pending offers, locale, chat log, etc.), mostly 4h TTL. `src/services/session.service.ts` is a set of thin typed wrappers; the Redis client and the Redis-or-memory fallback logic live once in `src/services/cache.service.ts` (`setJSON`/`getJSON`/`setString`/`setFlag`/`hasKey`/`claimKey`/`deleteKey`…) — add new session state as a one-line wrapper there, never a new hand-rolled Redis/Map pair. Every write is mirrored to an in-memory map with the same TTL; reads prefer Redis and fall back to memory whenever the client isn't `isReady`, switching back automatically when Redis recovers. Boot waits at most 5s for Redis (`redisReady`) before starting in memory mode.

### Final invoice generation (Primavera ERP integration removed 2026-07-23)

The final tax invoice sent to the customer on payment approval (`payment.service.ts` → `generateInvoicePDF` from `pdf.service.ts`, called after `approved` status, followed by `sendFinalInvoiceWhatsApp`) is now **only** Rede Peças' own PDFKit-rendered invoice — the same PDF that used to be the "mock" fallback when `PRIMAVERA_API_TOKEN` was unset is now the sole, permanent implementation. `generatePrimaveraInvoice` (which POSTed to a Primavera ERP `/api/facturas` endpoint for an AGT-certified invoice, falling back to the mock PDF on any error) was deleted outright, along with `config.primavera` (`config.ts`) and `PRIMAVERA_API_URL`/`PRIMAVERA_API_TOKEN` (`.env.example`) — there is no fallback branch anymore since there's nothing left to fall back from. The rest of the payment/order flow is unchanged; this only affects which code path renders the final invoice PDF. The message-catalog key backing this PDF's text was renamed `pdf.mockInvoice` → `pdf.invoice` (`src/i18n/messages.ts`, both `pt`/`en`) to match — it's not a mock anymore.

### No conversational AI agent — but six single-shot Claude calls

There is no conversational AI agent anywhere in the WhatsApp flow: routing, state, and every decision about what happens next are deterministic (the pipeline above). Product search (`productService.searchAndRespond`) is a deterministic full-text query against the inventory DB — the customer's search phrase must match on **every** word (`AND_TSQUERY`, so "engine oil" can't surface a timing belt tagged "engine"); only the subcategory-scoped "find an alternative" flows use any-word matching (`matchMode: 'any'`). Results are sent as a WhatsApp **List Message** (`sendWhatsAppList`, up to 3 rows, cheapest first); the customer's reply (row tap or typed digit) is resolved deterministically. "Talk to a human" is a plain keyword match (`HUMAN_HANDOFF_PATTERN`), not an AI inference.

There are six Claude call sites, all in `src/services/`, all on `claude-haiku-4-5-20251001`. Each is a single-shot call with no conversation history, and each degrades to deterministic behavior on any API failure:
- `humanize.service.ts`'s `humanize` — rewrites every outgoing customer message (via `reply.service.ts`'s `sendReply`/`sendReplyButtons`/`sendReplyList`) in the "Xico Peças" counter-clerk persona (`src/i18n/persona.ts`) in the customer's locale. **Off unless `CLAUDE_MESSAGE_ENABLED=true`.** The persona is polite/professional "tu" — no slang ("mate", "ó pá", "meu!"…) — and Portuguese is Angolan (European-Portuguese norm), never Brazilian ("pô", "né", "a gente", "estou verificando" are rejected). Rewrites are validated (language, length limit, numbers and quoted literals preserved, optional `preserve` bold terms, no added slang — `SLANG_PATTERNS`) and cached 24h by content hash plus a hash of the persona prompt (`humanized:<locale>:<promptHash>:*` keys, so a persona edit invalidates old rewrites); any failure or rejected rewrite sends the original canned text. 5s timeout, no retries. Admin pushes and raw `whatsapp.service.ts` sends bypass it.
- `ai.service.ts`'s `extractProductNames` — splits a free-text request into distinct part phrases (one → single search, 2+ → basket), or returns `[]` when the message isn't a part request at all (the caller then never searches). Runs **before** the "which vehicle?" question, and the result is carried through it (`DeferredPartRequest.productNames`), so it's called once per request. Fails open (`null`) to "treat the whole message as one search".
- `ai.service.ts`'s `extractVehicleDetails` (added 2026-10-27) — pulls make/model/year out of a manual vehicle-entry reply (step 12); every value is still validated by `validateFreeText`/`isPlausibleYear`. Fails open (`null`) to "the raw reply is the current step's field".
- `ai.service.ts`'s `extractDataWithClaudeVision` — vehicle document/VIN photo extraction, wired in via `processVehicleDocument`.
- `ai.service.ts`'s `extractPaymentProofData` — payment-proof extraction, wired in via `processPaymentProof` in `payment.service.ts`. Runs on **both** photo and PDF proofs (as of 2026-07-13) — the call sends an `image` or `document` content block to Claude depending on `mediaType`, so neither media type bypasses validation. A proof that comes back `valid: false` (e.g. not actually a receipt, illegible, blank) sends a generic "couldn't confirm this is valid, please resend" message with a "Try again" button (`t.payment.proofInvalid`/`proofRetryButtons`) — same reason-not-leaked-to-customer pattern as `document.invalid()` below, Claude's actual `reason` is logged server-side only — and does **not** advance `orders.status` or create an admin alert; only a validated proof does both.
- `validation.service.ts`'s `validateFreeText` (added 2026-07-27) — a text-only plausibility check for customer-typed name/address and vehicle make/model, since those fields have no fixed format a regex could validate (e.g. "is this a real Angolan address" isn't a pattern-matchable question). Like the others it's a single-shot judgment call, not a conversation — no history, no system prompt, no JSON action dispatch. It **fails open** (treats the input as valid, logs the error) on any network/API failure, so an Anthropic outage never blocks registration or vehicle onboarding — only the model's own judgment, or a malformed JSON response that came back at all, causes a rejection. NIF format, engine numbers, license plates, and VIN check digits are validated deterministically instead (same file), not via AI, since those have no semantic content an LLM could usefully judge.

Neither Vision call ever sees customer chat text — both take image/document input only. `validateFreeText` sees a single already-collected field value; `extractProductNames` sees the one search message; `humanize` (when enabled, with `contextual: true`) sees the customer's first name and their latest message. None of them sees the conversation history, and none dispatches actions — the model only ever returns text/JSON that deterministic code validates. There is no Redis-held conversation history for AI use anywhere in this codebase — the 25h `chatlog:<phone>` transcript written by `appendChatMessage` is never sent to Claude, and as of 2026-10-15 nothing reads it back via `getChatLog` either. The old rolling 20-message `session:<phone>` key and `getHistory`/`saveHistory` were removed as dead weight along with the agent that used them.

### Intended end-to-end workflow (agreed with Vivek, 2026-07-02; registration/vehicle split reversed 2026-07-07)


- **Onboarding was a single merged flow from 2026-07-02, split back into two independent state machines on 2026-07-07** (registration and vehicle ID have their own status again — see the message pipeline above): the merge made it impossible to resume "just the vehicle" for a returning customer whose vehicle session expired without also re-checking profile status, and complicated adding more independent-status entities (e.g. suppliers) the same way later.
- **Image routing is now state-aware** (implemented 2026-07-02): resolved as part of the same change, since it was a hard prerequisite for wiring in Vision. Still keyed off `needsVehicleId` after the 2026-07-07 split, just computed differently.
- **Staff/admin WhatsApp notification trigger moving to order creation** — still **not implemented as a trigger-point change**; the trigger still fires when a payment proof lands or presential payment is chosen. The delivery mechanism did change on 2026-07-1x: instead of pushing a WhatsApp message to the admin's own phone, it now writes to the `admin_alerts` feed (see above). No email notification — none exists in this codebase and none was added to scope.

Refund tracking on order rejection was explicitly decided *against* — it stays a message-only "refunded within 3–5 business days" notice with no new order status, consistent with payment gateway integration being out of scope per the SOW.
